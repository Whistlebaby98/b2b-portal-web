# 企采云对公商城前端 MVP 设计说明

## 1. 文档定位

本文档把已完成的需求访谈（Q1–Q22）收敛为一个可演示、可验收、可继续扩展的客户侧对公商城 MVP。目标是先验证“企业客户能否顺畅找到合适的 SKU、按组织权益完成结算并提交订单”，而不是一次性实现完整的交易后端或审批工作台。

技术基线为 TypeScript、Next.js（React）和 Tailwind CSS。Q2 的共识是：本阶段界面和关键交互做完整，登录会话、价格/库存/订单等数据使用可替换的 mock；同时在数据访问处保留明确的 session/API seam，便于后续接入真实服务。Q15 的共识是：所有订单提交后均进入待审批，买方端不提供审批按钮，详见 [ADR 0001](./adr/0001-mvp-order-approval.md)。

## 2. 产品目标与边界

### 2.1 MVP 要解决的问题

- 让企业买方在当前客户组织下浏览目录、搜索 SKU、查看协议价和促销。
- 让买方清楚知道价格、库存/交期、优惠、税费、收货和开票资料如何影响订单。
- 让买方可以从单品或批量清单建立购物车，并在一次结算流程中提交采购订单。
- 让买方能查看订单和“待审批”状态，知道下一步由谁/哪个组织流程处理。
- 用可替换的模拟数据验证信息架构、视觉层级、响应式布局和关键状态。

### 2.2 MVP 不做的事

- 不实现真实身份认证、企业资质审核、单点登录或多因素认证。
- 不实现真实库存锁定、仓储履约、物流追踪、支付网关或自动开票。
- 不实现客户侧审批工作台、审批/驳回按钮、审批链配置和外部 OA 回写。
- 不承诺真实价格、额度或交期；mock 数据只用于界面演示，不能作为交易依据。
- 不做供应商入驻、采购方运营后台、复杂报表、合同签署和售后工单。

## 3. 已确认的业务决策

| 主题 | MVP 决策 | 设计含义 |
| --- | --- | --- |
| 服务对象 | 面向企业客户的买方商城 | 默认进入采购工作台/商城首页，而非面向个人消费者的首页 |
| 组织语境 | 用户代表一个当前客户组织采购 | 所有价格、购物车和订单都绑定 `ActiveOrganizationContext` |
| 价格 | 支持组织协议价、阶梯价和活动优惠的展示 | 价格显示必须能解释“为什么是这个价格” |
| 选品 | 支持商品目录、SKU/OEM 搜索、筛选和批量采购清单 | SKU 是可交易单位，批量输入先解析再进入购物车 |
| 结算 | 收货地址、开票资料、结算条款为结算确认的一部分 | 提交前集中展示金额与资料摘要 |
| 订单 | 每笔提交成功的订单都生成待审批请求 | 订单初始状态统一为“待审批” |
| 审批 | 买方侧只读展示审批状态和时间线 | 不显示审批、驳回或改审批人的按钮 |
| 数据形态 | 完整 UI + mock 数据 + 可替换 session/API seam | 不把 mock 结构散落在页面组件中 |
| 后续演进 | 先验证主路径，再补充组织政策和交易后能力 | 通过领域对象和状态机保留扩展点 |

## 4. 用户、权限与组织上下文

### 4.1 MVP 角色

1. **买方用户（BuyerUser）**：浏览、搜索、加购、创建结算会话、提交订单、查看本人所属组织的订单。
2. **组织内审批人（概念角色）**：负责后续审批服务中的处理；本期不在买方商城中提供审批操作界面。
3. **商城运营/服务人员（系统外角色）**：提供目录和活动数据；本期不实现运营后台。

### 4.2 会话边界

页面加载时得到一个 `SessionSnapshot`（当前用户、可用组织列表、当前组织、成员职责和能力标识）。在真实接入前，snapshot 来自固定 mock fixture；未来替换为会话服务时，页面不应改动业务组件。

当前 MVP 按 Q8 采用“单一演示企业 + 采购员角色”：页面展示当前组织上下文，但暂不提供多组织切换、成员权限管理或跨组织购物车隔离 UI。下面关于组织切换和服务端授权的约束，是接入真实 session/API 时必须保持的目标契约。

必须满足：

- 没有有效的当前组织时，禁止建立购物车和提交订单，并给出切换/选择组织的引导。
- 切换组织时清空或隔离当前购物车和结算会话，不得沿用另一组织的价格或资料。
- 订单列表只返回当前组织且用户有权查看的订单；前端隐藏按钮不等于权限控制，真实权限必须由服务端再次校验。

## 5. 信息架构与模块清单

### 5.1 MVP 模块

| 模块 | 核心内容 | 关键状态 | 优先级 |
| --- | --- | --- | --- |
| 商城首页/采购工作台 | 企业权益、促销入口、推荐商品、待办摘要、采购车入口 | 加载、空态、错误、组织未选择 | P0 |
| 商品目录 | 分类、搜索、SKU/OEM 搜索、筛选、排序、协议价/阶梯价、库存与交期 | 初始、搜索中、无结果、筛选后 | P0 |
| 促销中心 | 活动卡片、适用商品、门槛、有效期、规则说明 | 生效、未开始、已结束、不可用 | P0 |
| 商品详情 | 规格、SKU、包装/单位、价格梯度、可售量、交付承诺、促销 | 可售、低库存、不可售、数量校验失败 | P0 |
| 批量采购 | 文本粘贴或模板导入 SKU/数量、解析结果、错误行修正 | 解析中、部分成功、全失败、已加入购物车 | P0 |
| 购物车 | 行项目编辑、删除、失效提示、金额摘要、去结算 | 空、正常、价格变化、库存不足 | P0 |
| 结算 | 收货地址、开票资料、结算条款、优惠和总额确认、提交 | 草稿、校验失败、提交中、提交成功 | P0 |
| 订单中心 | 订单列表、筛选、搜索、状态标签、金额和提交时间 | 空、加载失败、分页/加载更多 | P0 |
| 订单详情 | 行项目、金额快照、收货/开票摘要、审批时间线、下一步说明 | 待审批、已通过、已驳回、已取消（演示状态） | P0 |
| 组织与账户 | 当前组织切换、成员信息、通知入口 | 组织切换确认、资料缺失 | P1（壳层） |

### 5.2 后续模块（不阻塞 MVP）

组织资质与成员管理、可配置审批政策、真实支付/授信、库存预留、履约与物流、发票开具、合同签署、售后、运营活动配置、数据报表和通知中心。

## 6. 路由与页面职责

路由名是产品级信息架构约定；实现可以采用同等语义的 Next.js 路由，但页面不能依赖某个具体 mock fixture 才能成立。

| 路由 | 页面职责 | 主要入口/出口 |
| --- | --- | --- |
| `/` | 商城首页/采购工作台：权益、活动、推荐和待办摘要 | 进入目录、促销、购物车、订单 |
| `/promotions` | 活动列表与规则说明 | 活动详情、适用 SKU |
| `/promotions/[campaignId]` | 单个活动的适用范围、门槛和商品 | 商品详情、加入购物车（后续迭代） |
| `/products` | 商品目录、分类、搜索、筛选、排序 | SKU 详情、批量采购 |
| `/products/[id]` | SKU 详情与数量选择 | 加购、去购物车 |
| `/bulk-buying` | 粘贴/导入采购清单、解析反馈 | 加入购物车、修正错误 |
| `/cart` | 购物车编辑与价格/库存提醒 | 进入结算 |
| `/checkout` | 结算资料和金额确认 | 提交订单、返回购物车 |
| `/orders` | 当前组织订单列表 | 订单详情 |
| `/orders/[orderId]` | 订单快照、待审批状态和时间线 | 返回订单列表、联系组织负责人（占位） |
| `/account` | 当前组织和买方账户摘要 | 切换组织、查看资料（壳层） |

未登录或会话失效时，页面应显示统一的登录/会话占位态；真实登录路由和鉴权由后续身份服务决定。

## 7. 页面与组件设计

### 7.1 全局壳层

- 顶部：品牌、全局搜索、通知、当前组织切换、购物车数量。
- 桌面端侧栏：工作台、商品目录、促销、批量采购、订单中心、账户。
- 移动端：侧栏折叠为抽屉，保留搜索、购物车和组织切换的可达入口。
- 页面统一提供面包屑、页面标题、状态反馈和返回路径。

### 7.2 商品卡片与价格解释

商品卡片至少展示商品名、SKU、品牌/关键规格、企业协议价、原价或优惠说明、最小起订量、库存/交期和数量控件。阶梯价使用可扫描的表格/提示，不把一长串规则塞进按钮。

价格区域要区分：

1. 当前组织可用的成交单价；
2. 达到数量门槛后的潜在单价；
3. Campaign 带来的优惠；
4. 税费、运费或结算条款尚未确定的部分。

### 7.3 结算摘要

结算页采用“资料确认 + 金额确认 + 提交”三段式布局。用户可以回到购物车修改行项目，但在提交前必须重新显示价格、促销、库存、收货地址、开票资料和结算条款的校验结果。

### 7.4 订单状态展示

订单详情顶部使用明确的状态标签：“待审批”。时间线至少包含“已创建订单”和“已提交审批请求”两项；审批人未知时显示“等待组织审批流程处理”，不能编造姓名或预计完成时间。买方页面不出现审批/驳回主按钮。

## 8. 数据与 API seam

### 8.1 前端领域数据

页面应围绕 `CustomerOrganization`、`BuyerUser`、`ActiveOrganizationContext`、`Product/SKU`、`PriceOffer`、`Campaign`、`Cart`、`CheckoutSession`、`Order`、`ApprovalRequest`、`ShippingAddress`、`InvoiceProfile`、`PaymentTerm` 组织数据，定义见 [CONTEXT.md](../CONTEXT.md)。

建议的读取/写入能力边界如下（本期可由 mock adapter 实现）：

```text
session.getSnapshot()
organization.listAvailable()
catalog.search(query, filters, organizationId)
catalog.getSku(sku, organizationId)
campaign.list(organizationId)
cart.get(organizationId) / cart.mutate(command)
checkout.create(cartId) / checkout.validate(sessionId) / checkout.submit(sessionId)
orders.list(organizationId, query) / orders.get(orderId)
```

每个 adapter 返回明确的 `loading | success | empty | error` 结果和可展示的错误码；页面组件不直接读取随机 JSON 或在渲染期间修改全局 mock 状态。写入操作需要幂等键（尤其是提交订单），以便未来接入真实服务。

### 8.2 mock 数据原则

- 固定一组客户组织、买方、SKU、活动、地址、开票资料和订单，覆盖正常、空、低库存、价格变化、提交失败等状态。
- mock 价格必须带 `source`/`reason` 文案，例如“企业协议价”“活动满额优惠”，避免把演示数字误认为真实承诺。
- mock session 可以模拟组织切换和能力标识，但不模拟绕过权限的行为。

## 9. 状态机

### 9.1 购物车

```text
EMPTY --add SKU--> ACTIVE
ACTIVE --edit quantity--> ACTIVE
ACTIVE --remove last line--> EMPTY
ACTIVE --price/stock recheck fails--> NEEDS_REVIEW
NEEDS_REVIEW --user accepts/revises--> ACTIVE
```

购物车状态只表示编辑和校验，不表示库存锁定或订单成立。

### 9.2 结算会话

```text
CREATED -> VALIDATING -> READY_TO_SUBMIT
    |          |                |
    |          v                v
    |       INVALID          SUBMITTING -> SUBMITTED
    |                              |
    +---------- EXPIRED <----------+
```

`READY_TO_SUBMIT` 仅说明当前资料和金额通过一次校验；提交服务仍需在服务端重新校验价格、库存、组织权限和额度。

### 9.3 订单与审批

```text
CHECKOUT_SUBMITTED
        |
        v
ORDER_SUBMITTED + APPROVAL_PENDING
        |
        +--> APPROVAL_APPROVED -->（后续履约）
        |
        +--> APPROVAL_REJECTED
        |
        +--> ORDER_CANCELLED / REQUEST_EXPIRED（按后续政策开放）
```

MVP 只要求客户端可靠展示 `ORDER_SUBMITTED + APPROVAL_PENDING`；其他状态可由 fixture 演示，但不得让买方在页面上执行审批动作。

### 9.4 促销资格

```text
NOT_ELIGIBLE -> ELIGIBLE_PREVIEW -> CONFIRMED_AT_CHECKOUT
       ^                              |
       +--------- EXPIRED/CHANGED <---+
```

活动卡片上的“预计优惠”不是成交承诺，最终资格以结算和订单提交时的校验为准。

## 10. 端到端业务流程

### 流程 A：发现商品并加购

1. BuyerUser 进入首页，系统加载 ActiveOrganizationContext。
2. 用户通过分类、关键词或 SKU/OEM 编码进入目录。
3. 系统展示当前组织可见的 Product/SKU、PriceOffer、Campaign、InventoryAvailability 和 DeliveryPromise。
4. 用户在详情页选择数量；前端校验最小起订量、包装倍数和正整数规则。
5. 加入 Cart，显示行数、数量和金额提示；不锁定库存。

### 流程 B：批量采购

1. 用户粘贴“SKU + 数量”或选择模板文件。
2. 系统逐行解析，报告无法识别的 SKU、数量格式、重复项和不可售项。
3. 合法行匹配当前组织价格和活动，用户确认后一次性加入 Cart。
4. 任何部分失败都保留成功行，并允许用户修正失败行后重试；不得静默丢弃输入。

### 流程 C：结算与提交

1. 用户从 Cart 进入 CheckoutSession。
2. 选择或新增 ShippingAddress、InvoiceProfile 和 PaymentTerm。
3. 系统校验组织权限、价格/促销、库存/交期、最小起订量、税务资料和授信/结算条件。
4. 页面展示商品小计、优惠、税费、运费（如有）和订单总额，并标注仍可能变化的项目。
5. 用户确认后提交；提交按钮进入 loading，避免重复点击。
6. 成功后创建 Order 与 ApprovalRequest，跳转订单详情并显示“待审批”。失败时保留结算内容，逐项解释可修复问题。

### 流程 D：查看订单

1. 用户在订单中心按状态、时间、订单号或 SKU 搜索。
2. 打开详情查看提交时的行项目、金额、收货/开票摘要和审批时间线。
3. 待审批订单只显示只读状态和下一步说明；不提供审批或驳回按钮。
4. 若后续服务回写已通过/已驳回，页面刷新后展示新状态和时间，不改写历史快照。

## 11. 关键业务规则与校验

- 当前组织必须有效，且 BuyerUser 对目标 SKU、地址、开票资料和结算条款有访问权限。
- 数量必须满足 SKU 的最小起订量、包装倍数和可售上限；输入错误要指出具体行和原因。
- 价格优先匹配当前组织的有效 PriceOffer，再叠加符合条件的 Campaign；过期活动不得继续使用。
- 购物车中的价格、库存、活动资格和交期只是一种提示；CheckoutSession 验证和提交时必须重新核验。
- ShippingAddress、InvoiceProfile、PaymentTerm 必须在提交时形成快照，历史订单不能随资料簿更新而改变。
- 订单提交操作需要防重复提交；客户端重试应能识别同一个幂等结果。
- 所有成功提交的订单都进入 ApprovalRequest“待审批”，即使订单金额很低或买方职责看起来具备审批资格。
- 买方商城不通过隐藏/显示按钮实现真正授权；后端接入后仍须在服务端校验组织和用户权限。
- 金额、税率和数量使用明确的小数/整数规则，展示层不能用浮点格式化替代业务计算。

## 12. 验收场景（MVP）

### 场景 1：组织协议价加购

**Given** 买方已选择客户组织，某 SKU 有有效协议价和可售库存。
**When** 买方搜索 SKU、选择合法数量并点击加购。
**Then** 购物车显示 SKU、数量、协议价和价格来源；首页/目录的购物车数量同步增加。

### 场景 2：活动门槛提示

**Given** 某 Campaign 要求购买满指定数量。
**When** 买方数量未达门槛并进入结算。
**Then** 页面展示当前优惠与还差多少的说明，不把潜在优惠计入已确认总额；达到门槛并重新校验后才显示生效。

### 场景 3：批量清单部分成功

**Given** 输入包含两个有效 SKU 和一个不存在的 SKU。
**When** 买方执行解析并确认。
**Then** 两个有效行进入购物车，失败行保留并说明原因；页面提供修正/重试入口，不静默忽略失败行。

### 场景 4：提交订单进入待审批

**Given** 购物车、收货地址、开票资料和结算条款均通过校验。
**When** 买方确认金额并提交一次。
**Then** 生成唯一订单号和 ApprovalRequest，订单详情显示“待审批”；页面不出现审批或驳回按钮。

### 场景 5：提交校验失败可修复

**Given** 购物车中的某 SKU 库存已变化或 InvoiceProfile 缺少税号。
**When** 买方提交结算。
**Then** 提交被阻止，错误定位到具体行/资料，已填写内容保留，买方修正后可再次校验。

### 场景 6：组织隔离

**Given** 用户属于两个客户组织且在组织 A 有购物车。
**When** 用户切换到组织 B。
**Then** 组织 B 只看到自己的价格、资料、购物车和订单；切回组织 A 后可以恢复组织 A 的购物车，不发生跨组织混淆。

### 场景 7：响应式与可访问性

**Given** 用户在手机宽度和桌面宽度访问任一主流程页面。
**When** 用户通过键盘或触控完成搜索、加购、结算和查看订单。
**Then** 主要操作可见且可聚焦，状态变化有文本反馈，表格/卡片不发生横向溢出，颜色不是表达状态的唯一方式。

## 13. 视觉与交互基线

- 采用稳定的企业级信息层级：深色品牌导航、浅色内容背景、明确的状态色和低噪声卡片。
- 主操作每个视口只保留一个清晰的视觉优先级；危险或不可逆动作需要二次确认。
- 空态说明“为什么为空”和“下一步做什么”；错误态提供重试和人工处理路径；加载态避免页面跳动。
- 金额、数量和状态标签使用统一格式；中文文案避免把“待审批”写成“处理中”或“已确认”。
- 所有图标按钮提供可读的 aria-label/tooltip，表单控件拥有可见标签和错误关联。

## 14. 非功能要求与验证方式

### 性能

首屏优先加载首页摘要和首屏商品，列表采用分页/加载更多；图片和非关键模块可延迟加载。验收时在常见桌面和移动视口检查无明显布局抖动。

### 可靠性

每个读取/写入状态都有 loading、empty、error 和 retry；提交订单有幂等键和成功后的明确跳转。mock adapter 应能注入延迟和错误，覆盖异常路径。

### 安全与隐私

不在前端硬编码真实企业、税号、额度或凭证；日志和错误提示不得泄露跨组织数据。真实接入时由服务端执行组织、成员和订单权限校验。

### 可观测性

记录搜索、查看 SKU、加购、创建结算、校验失败、提交成功/失败和订单详情查看等产品事件；事件携带匿名会话和组织上下文标识，不携带完整税号、地址或发票敏感字段。

## 15. 推荐实现顺序

1. 建立全局壳层、mock session 和 ActiveOrganizationContext。
2. 完成目录/详情/价格卡片及加购状态。
3. 完成购物车和批量采购解析反馈。
4. 完成结算资料、金额摘要和提交成功/失败状态。
5. 完成订单列表/详情与待审批时间线。
6. 补齐促销中心、组织切换、响应式和可访问性验收。
7. 用真实接口契约替换 mock adapter，保持页面领域模型和状态机不变。

## 16. 后续范围与演进路线

### P1：交易闭环

真实会话与组织切换、目录/价格/库存接口、订单幂等提交、授信额度和支付/线下对公结算、库存预留、履约状态。

### P2：组织治理

审批政策配置、分级审批、预算校验、审批工作台、外部 OA/ERP 回写、成员与职责管理、通知订阅。

### P3：运营与服务

活动配置、个性化推荐、合同与电子签署、发票状态、售后、报表、供应商和多仓配送。

每一阶段都应先更新领域词汇和状态机，再扩展页面操作，避免将后端状态直接映射成含义不清的 UI 标签。

## 17. 待调研问题

以下问题不阻塞当前 MVP，但在接入真实服务前必须得到业务确认：

- 客户组织是否允许自动通过、是否存在按金额/品类/预算的例外审批政策？
- 待审批期间价格、促销、库存和授信额度是否锁定，锁定时长如何定义？
- 买方能否撤回或取消待审批订单，撤回后是否释放库存/额度？
- 订单审批通过后，支付、发票、合同和履约由哪个系统承接？
- 一个 BuyerUser 代表多个组织时，通知、地址簿和订单检索的默认范围是什么？
- 交期是发货承诺还是到货承诺，跨仓拆单如何在订单详情表达？
